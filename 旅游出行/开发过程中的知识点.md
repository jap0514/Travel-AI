4、@NotNull`、`@NotBlank

**`@NotNull`**

- **适用类型**：任何类型（String、集合、数组、包装类、自定义对象等）。
- **校验逻辑**：对象不能为 `null`。
- **可通过的情况**：空字符串 `""`、空集合、空白字符串 `" "` 都认为**通过**（因为不是 `null`）。

**`@NotBlank`**

- **适用类型**：**仅适用于字符串**（`CharSequence` 及其子类，如 `String`）。
- **校验逻辑**：`null` 或 **去除首尾空白字符后长度为 0** 都不通过。
- **可通过的情况**：字符串包含至少一个**非空白字符**。例如 `" a "`（去除空白后 `"a"`）通过，`""` 或 `" "` 不通过。

8、序列化问题

MySQL的JDBC在往数据库存一个 Java 对象的时候，底层会用 ObjectOutputStream 把对象序列化成一个字节数组，然后存进 BLOB/TEXT 字段。

底层 ObjectOutputStream 会调用 writeObject() 方法，这就要求对象必须实现 Serializable 接口，例如：public class DailyActivity implements Serializable    但是这个只是一个标记接口，没有任何业务方法，它告诉 JVM 这个对象是可以被序列化的。如果不加这个的话，就会抛 NotSerializableException 的异常。

10、外键约束

判断是否需要外键时，需要多方面考虑。

优势：数据可以做到绝对兜底，外键约束可以做到100%杜绝脏数据，比如一些孤儿订单或无效房间号等。可以在删除父数据时子数据自动处理。



劣势：

高并发性能杀手：当一个房间，有2000个用户同时下单，如果没有外键时，就只管往订单表中插入一条记录就好，检查完唯一约束后就写入磁盘，速度、QPS是非常快的。但如果订单表存在物理外键，去指向房间，在插入数据的时候就需要对房间表中的对应房间加一个共享锁（S锁），去校验房间是否存在。但这就会造成一个问题，2000个用户都要去抢这个锁，虽然S锁之间不互斥，但是MySQL内部需要有锁的管理开销。

分库分表的天敌：当数据在单库容量撑不住的时候，就需要做业务的垂直拆分，当房间表和1订单表不在同一个库时，物理外键就会失效，MySQL的外键约束不支持跨数据库实例，并且当需要迁移订单数据到新库时，又会因为外键而报错。删除掉外键的话，订单表就没有了物理约束，且之前依赖于数据库的校验全部失效。

引发死锁与运维噩梦：如果在高并发的时候，需要对房间表新增一个字段，在没有外键的时候，通过ALTER很轻松可以完成操作；但是如果有了外键，在部分MySQL版本中，需要等待所有持有房间表的锁的事务结束，但此时是高并发，有海量订单需要插入。就会导致ALTER TABLE 进入“等待元数据锁”状态，阻塞了后续所有对该房间表的查询（比如酒店详情页面、搜索页面、查询房间接口都用不了）。

联级删除风险不可控：如果设置了 `ON DELETE CASCADE`（级联删除），当在删除酒店的时候就会把酒店下面的所有房间，房间下面的所有订单全部删除。

13、

XML里面做SQL查询的时候，查询的字段需要和 resultType 里面连接的实体类型对应上，才做返回处理。

如果想要返回的是自己弄的 VO 实体，就需要在 XML 文件中弄一个 resultMap 来映射，resultMap 里面的每一个 result 都做一个映射，result 里面的 property 是 需要使用的 VO 实体里面的字段，column 是和SQL查询里面需要查询的字段对应的。

```java
<resultMap id="EmptyRoomResultMap" type="com.travel.vo.HotelEmptyRoomVO">
    <result property="hotelId" column="hotel_id" jdbcType="BIGINT"/>
    <result property="hotelName" column="hotel_name" jdbcType="VARCHAR"/>
    <result property="roomTypeId" column="room_type_id" jdbcType="BIGINT"/>
    <result property="roomTypeName" column="room_type_name" jdbcType="VARCHAR"/>
    <result property="roomNo" column="room_no" jdbcType="VARCHAR"/>
    <result property="hasEmptyRoom" column="has_empty_room" jdbcType="BOOLEAN"/>
    <result property="availableBookTime" column="available_book_time" jdbcType="TIMESTAMP"/>
</resultMap>
    
<select id="selectEmptyRoom" resultMap="EmptyRoomResultMap">
        select
            h.hotel_id,
            h.name as hotel_name,
            hrt.room_type_id,
            hrt.name as room_type_name,
            hr.room_id,
            hr.room_no,
            case
                when not exists(
                        select 1 from hotel_booking hb
                        where hb.room_id=hr.room_id
                          and hb.check_in_date &lt; #{endDate}
                          and hb.check_out_date &gt; #{startDate}
                ) then true
                else false
            end as has_empty_room,
            case
                when not exists(
                        select 1 from hotel_booking hb
                        where hb.room_id=hr.room_id
                          and hb.check_in_date &lt; #{endDate}
                          and hb.check_out_date &gt; #{startDate}
                ) then NOW()
                else (
                    select min(hb2.check_out_date)
                    from hotel_booking hb2
                    where hr.room_id=hb2.room_id and hb2.check_out_date &gt; #{startDate}
                    )
            end as available_book_time
        from hotel h
        join hotel_room_type hrt on h.hotel_id=hrt.hotel_id
        join hotel_room hr on hrt.room_type_id=hr.room_type_id and h.hotel_id=hr.hotel_id
        where h.city=#{city}
    </select>
```

如果在代码里面从数据库中获得了 LocalDateTime 对象，直接通过Spring Boot 的 @RestController 返回给前端的话，Spring Boot 会默认使用 Jackson 框架将 Java 对象序列化为 JSON，而 Jackson 对于 LocalDateTime 类型的默认序列化格式就是 ISO 8601，所以就会自动在日期和时间中间加个 T（2026-07-12T00:00:00）。

（1）可以在返回的 VO 实体的字段加上@JsonForma就可以了

```java
@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss",timezone = "GMT+8")
```

（2）也可以在 application.yml 文件中做全局配置

```java
spring:
  jackson:
    date-format: yyyy-MM-dd HH:mm:ss
    time-zone: GMT+8
```

18、LangGraph 的 `interrupt_before` 机制不适合跨 HTTP 请求场景

**问题**：`interrupt_before=["user_interaction"]` 会让图在**每次**路由到 `user_interaction` 时都暂停，而不是只在第一次需要等待用户输入时暂停。

**原因**：`interrupt_before` 是为单次请求内的挂起设计的，无法区分"第一次应该暂停"和"后续请求恢复后应该继续"。

**解决**：移除 `interrupt_before`，改用 `interaction_interrupted` 标记来控制。

```python
# 错误做法：每次都中断
multi_agent = workflow.compile(interrupt_before=["user_interaction"])

# 正确做法：通过 interaction_interrupted 标记控制
multi_agent = workflow.compile()
# 第一次：无有效用户输入 → 设置 interaction_interrupted=True → 返回 END
# 第二次：清除 interaction_interrupted → 正常处理用户输入
```





19、`interaction_interrupted` 标记的作用

**机制**：
- 当 `user_interaction_node` 检测到没有有效用户输入时，设置 `interaction_interrupted=True`
- `supervisor` 检测到这个标记后，返回 `{"next": "END"}` 结束图执行
- `process_with_agent` 检测到 `interaction_interrupted=True`，保存 flow state 到 Redis，然后返回给 Java

**恢复时**：从 Redis 恢复 state 时，清除 `interaction_interrupted=False`，让后续请求能正常进入 `user_interaction_node` 处理用户输入。

```python
# user_interaction_node.py
if status and status.startswith("waiting_") and messages:
    last_msg = messages[-1]
    if not isinstance(last_msg, HumanMessage):  # 没有有效用户输入
        return {"interaction": {"**interaction, "interaction_interrupted": True}}

# supervisor.py
if interaction.get("interaction_interrupted"):
    return {"next": "END"}

# process_with_agent.py 恢复时
if interaction.get("interaction_interrupted"):
    interaction["interaction_interrupted"] = False  # 清除标记
```





20、Flow State 序列化问题

**问题**：`messages` 里包含 `HumanMessage`、`AIMessage` 等 langchain 对象，无法直接 JSON 序列化存入 Redis。

**解决**：实现 `_serialize_messages` 和 `_deserialize_messages` 函数，将消息对象转为 dict 再转回。

```python
def _serialize_messages(messages):
    result = []
    for msg in messages:
        msg_dict = {
            "type": type(msg).__name__,
            "content": msg.content,
        }
        if hasattr(msg, "additional_kwargs") and msg.additional_kwargs:
            msg_dict["additional_kwargs"] = msg.additional_kwargs
        if hasattr(msg, "name") and msg.name:
            msg_dict["name"] = msg.name
        result.append(msg_dict)
    return result

def _deserialize_messages(messages_data):
    from langchain_core.messages import HumanMessage, AIMessage, SystemMessage, ToolMessage
    result = []
    for d in messages_data:
        msg_type = d.get("type", "")
        content = d.get("content", "")
        additional_kwargs = d.get("additional_kwargs", {})
        name = d.get("name")
        if msg_type == "HumanMessage":
            result.append(HumanMessage(content=content, name=name, additional_kwargs=additional_kwargs))
        elif msg_type == "AIMessage":
            result.append(AIMessage(content=content, name=name, additional_kwargs=additional_kwargs))
        # ...
    return result
```

28、

静态方法属于类本身，而类上的泛型 `T` 是在**创建对象（new Result<>()）**时才能确定的。静态方法加载时根本不知道 `T` 是什么，所以**静态方法永远不能引用类上的 `T`**。

因此，只要静态方法想用泛型，**必须**在返回类型前自己声明一个新的 `<T>`（或者叫别的字母）。

```java
public class Result<T> {  // 类上的 T 静态方法用不了

    // ✅ 必须加 <T>，这是静态方法自己的 T，跟类上的 T 重名但没关系（各算各的）
    public static <T> Result<T> success(T data) {
        // ...
    }
}
```

@ResponseStatus(HttpStatus.BAD_REQUEST)

这个注解是用来强制修改HTTP协议层面的响应状态码的，如果不添加这个，不管业务代码是否执行成功都会返回状态码200，这个200仅仅是代表请求处理成功而已。

如果想要前端能够准确获取到后端业务执行的一个状况，就需要这个注解，配合自定义的状态码来统一管理

```java
  @ExceptionHandler(BusinessException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  public Result<Void> handleBusiness(BusinessException e, HttpServletRequest request) {
      log.warn("业务异常 | path={} | code={} | msg={}",
              request.getRequestURI(), e.getCode(), e.getMessage());
      return ResultUtil.fail(e.getCode(), e.getMessage());
  }
```

33、请求的过程：

1. **客户端请求** →
2. **过滤器（Filter）** 开始处理（执行 `doFilter` 前置逻辑）→
3. **经过所有过滤器后**，请求抵达 **DispatcherServlet（前端控制器）** →
4. **拦截器（Interceptor）** 开始处理（执行 `preHandle`）→
5. **进入 Controller（你的业务接口）** →
6. 返回响应时，按**相反顺序**执行拦截器的 `postHandle` 和 `afterCompletion`，再反向经过过滤器。





34、ContentCachingRequestWrapper的作用

在标准的 Servlet 规范中，HttpServletRequest 的请求体（Body）默认只能被读取一次，因为请求体（Body）本质上是网络传输中的字节流，数据是连续到达的，Java的 ServletInputStream 读取数据时，是通过游标（指针）向后移动的，这个流是单向的、不可重置的，当读完所有字节后，流就被消耗掉了，就不可以重新读。

但是如果在正常的业务 Controller 之前有过滤器或者拦截器，在里面已经读取了请求体的话，正常情况下，Controller 是读不到请求体了的，就会抛出异常：`HttpMessageNotReadableException: Required request body is missing`。

Spring 提供了 **`ContentCachingRequestWrapper`**（内容缓存请求包装器）。它把原始的输入流读取后，**复制一份副本保存到内存（或缓存）中**。后续无论是过滤器还是 Controller，读的都是这个副本，而不直接消耗原始流。

1. **请求体缓存是“被动”的**：必须在 `chain.doFilter()` **之后**调用 `getContentAsByteArray()`，否则缓存为空。
2. **响应体必须手动写回**：使用 `ContentCachingResponseWrapper` 后，**务必**调用 `copyBodyToResponse()` 方法，否则客户端将收不到任何响应

所以，如果是需要在 chain.doFilter() 之前获取 inputstream，就得用 CachedBodyHttpServletRequest
