## 一、项目背景

随着人工智能技术的快速发展，智能旅行规划成为旅游行业数字化转型的重要方向。传统旅行规划方式存在效率低、信息分散、个性化程度不足等问题，用户往往需要在多个平台间切换才能完成一次完整的旅行规划。

本项目旨在构建一个**基于多智能体（Multi-Agent）的智能旅行规划系统**，利用大型语言模型（LLM）、检索增强生成（RAG）技术、向量数据库和地图服务，为用户提供一站式的智能旅行规划服务。系统能够根据用户的需求（目的地、天数、预算、节奏偏好），自动完成信息收集、行程规划、方案评审与优化等全流程工作，输出结构化的旅行计划。

**目标用户**：有旅行规划需求的用户，特别是自由行游客
**建设目标**：实现一个可用的智能旅行规划后端服务，支持 Web API 调用，与前端应用集成

## 二、需求分析

### 2.1 目标用户分析

| 用户角色 | 需求描述 |
|---------|---------|
| 自由行游客 | 希望快速获得个性化行程规划，减少信息搜索成本 |
| 亲子家庭 | 关注行程节奏适中、景点适合儿童、安全性高 |
| 商务出行 | 时间紧张，需要高效、紧凑的行程安排 |
| 老年旅游 | 偏好轻松节奏，避免过度奔波 |

### 2.2 功能需求分析

**核心功能**：

1. **旅行目的地规划**：用户输入目的地、天数、预算、节奏偏好，系统生成完整行程
2. **旅游景点信息查询**：系统自动查询景点门票、开放时间、特色介绍等信息
3. **天气查询**：结合天气预报信息辅助行程安排
4. **酒店和交通推荐**：提供符合预算的住宿和交通建议
5. **行程草案评审**：通过多维度专家评审（可行性、预算、节奏、多样性）自动优化行程
6. **地图路线展示**：提供景点间路线规划，支持前端地图绑线展示
7. **用户偏好记忆**：系统记忆用户历史偏好，持续优化规划质量
8. **通用问答**：支持用户进行旅行相关的普通问答

**用户交互流程**：

```
用户输入需求 → 意图识别 → 旅行规划流程/问答流程
                          ↓
                        任务分析 → 信息研究 → 行程规划
                          ↓                    ↓
                      专家评审 ← 不合格 ← 方案修正
                          ↓ 合格
                      最终优化 → 输出行程
```

### 2.3 非功能需求分析

- **响应速度**：单次规划请求在30秒内完成
- **准确性**：行程规划内容真实可靠，景点信息有据可查
- **可扩展性**：Agent节点可独立扩展，支持新增功能模块
- **可观测性**：完整记录每个环节的输入输出，支持问题追踪
- **并发处理**：支持多用户同时使用（已识别并发风险并提供解决方案）

## 三、系统设计

### 3.1 总体架构

本系统采用**多智能体协作架构**，基于 LangGraph 图编排框架构建，整体分为以下层次：

```
┌─────────────────────────────────────────────────────┐
│                   Web API 层                         │
│         (FastAPI - /api/chat, /api/route)           │
├─────────────────────────────────────────────────────┤
│                   Service 层                         │
│    (travel_agent.py / multi_agent_travel.py)        │
├─────────────────────────────────────────────────────┤
│                   Agent 层                           │
│  Intent_Recognition / Supervisor / TaskAnalyzer     │
│  Researcher / Planner / Critic / Refiner          │
│  FinalOptimizer / ParsePlan / General_QA           │
├─────────────────────────────────────────────────────┤
│                   工具层 (MCP)                       │
│   Travel Tools Server (天气/酒店/航班)               │
│   Qdrant RAG Server (知识库检索)                    │
├─────────────────────────────────────────────────────┤
│                   存储层                             │
│   Redis (会话上下文/用户Profile)                     │
│   Qdrant (向量数据库/知识库)                         │
│   Mem0 (用户长期记忆)                               │
└─────────────────────────────────────────────────────┘
```

### 3.2 技术选型

| 技术类别 | 选型方案 | 说明 |
|---------|---------|------|
| LLM框架 | LangGraph | 多智能体图编排，支持条件路由、循环控制 |
| AI模型 | DeepSeek R1 (本地部署) | 支持本地化部署，降低成本 |
| 向量数据库 | Qdrant | 高性能向量检索，支持混合检索 |
| 全文检索 | BM25 + 向量混合检索 | 融合关键词和语义检索 |
| 重排序 | CrossEncoder | MS MARCO 微调模型，提升检索质量 |
| 会话存储 | Redis | 结构化存储会话上下文和用户Profile |
| 长期记忆 | Mem0 + Qdrant | 用户偏好和历史记忆持久化 |
| 地图服务 | 高德地图API | 地址解析、路线规划 |
| 天气API | 心知天气 | 天气预报查询 |
| 追踪系统 | Langfuse | LLM调用追踪和可观测性 |
| Web框架 | FastAPI | 高性能异步API服务 |

**Redis 存储结构**：

### 3.4 多智能体协作设计

系统定义了**9个专业Agent节点**，各司其职：

```
Intent_Recognition ──┬──→ "plan" → Supervisor
                    │
                    └──→ "qa"   → General_QA → END

Supervisor 负责任务调度，下一步流向：
├── TaskAnalyzer → Supervisor
├── Researcher  → Supervisor
├── Planner     → Supervisor
├── Critic      → Supervisor ──→ FinalOptimizer → Supervisor
│                  ↑              ↑
│                  └──── Refiner ←┘
└── ParsePlan → END
```

**Critic节点循环优化机制**：Critic通过4个专家（可行性、预算、节奏、多样性）对行程草案评分，总分<85分时进入Refiner修正，形成"评审-修正"循环，最多迭代3次。

## 四、系统实现

### 4.1 核心Agent节点实现

#### 4.1.1 Intent_Recognition（意图识别）

```python
# app/agents/Intent_Recognition.py
```
**功能**：接收用户原始输入，识别用户意图是"旅行规划"还是"通用问答"

**关键逻辑**：使用LLM结构化输出，判断意图分类

---

#### 4.1.2 TaskAnalyzer（任务分析）

**功能**：从用户需求中提取结构化任务信息

**输出**：
- 目的地（destination）
- 天数（days）
- 预算水平（budget）：低/中/高
- 节奏偏好（pace）：轻松/适中/紧凑
- 核心诉求（user_query）

---

#### 4.1.3 Researcher（信息研究）

**功能**：收集目的地全面信息，为行程规划提供数据支撑

**使用工具**：
- `search_classic_routes`：获取经典行程模板
- `search_attractions`：查询景点详情
- `search_user_plans`：参考真实用户行程
- `hybrid_search`：混合检索景点知识库
- `search_weather`：查询天气预报
- `search_hotels`：查询酒店推荐

**输出**：包含景点、交通、美食、住宿、天气的综合研究报告

---

#### 4.1.4 Planner（行程规划）

**功能**：基于研究报告生成完整行程草案

**规划原则**：
- 每天景点不超过4个（大型景点算2个）
- 充分利用公共交通
- 预算分配参考：经济型以门票+餐费为主，舒适型可体验高端项目
- 预留休息时间和收整行李时间

**输出**：按天组织的详细行程草案（Markdown格式）

---

#### 4.1.5 Critic（方案评审）

**功能**：并行调用4个专家对行程进行多维度评审

**4个评审专家**：

| 专家 | 权重 | 评审重点 |
|-----|------|---------|
| 可行性专家 | 40% | 时间安排、交通衔接、开放时间 |
| 预算专家 | 20% | 整体预算合理性、隐性消费风险 |
| 节奏专家 | 20% | 活动密度、休息时间、室内室外平衡 |
| 多样性专家 | 20% | 景点类型丰富度、同质化检查 |

**评分标准**：每项0-100分，加权总分≥85视为合格

**决策逻辑**：
- 总分≥85 → 进入`final_optimizer`最终润色
- 总分<85 → 进入`refiner`修正后再次评审
- 迭代达到3次 → 强制进入`final_optimizer`

---

#### 4.1.6 Refiner（方案修正）

**功能**：根据Critic的评审意见对行程进行针对性修正

**输入**：Critic返回的4个维度的评分和反馈意见
**输出**：修正后的行程草案

---

#### 4.1.7 FinalOptimizer（最终优化）

**功能**：对通过评审的行程进行最终润色，提升可读性和专业性

---

#### 4.1.8 ParsePlan（结构化解析）

**功能**：将最终行程解析为结构化数据

**输出结构**：
```python
TravelPlan:
  - title: 行程标题
  - destination: 目的地
  - days: 天数
  - budget: 预算
  - pace: 节奏
  - daily_plans: List[DailyActivity]
      - day: 第N天
      - theme: 主题
      - activities: 活动列表
      - location: 地点
      - transportation: 交通方式
      - estimated_cost: 预估费用
```

---

#### 4.1.9 General_QA（通用问答）

**功能**：处理用户非规划类咨询，如旅行常识、签证问题、必备物品等

### 4.6 关键算法——混合检索与重排序

**检索流程**：

```
用户查询 → 编码为向量 → 并行执行:
                           ├── 向量检索 (Top-K*2)
                           └── BM25关键词检索 (Top-K*2)
                        ↓
                   RRF融合排序
                        ↓
              CrossEncoder重排序 (Top-12 → Top-5)
                        ↓
                    返回结果
```

**RRF公式**：`score(q,d) = Σ 1/(k+rank_i(q,d))`，其中k=60

## 七、项目总结

### 7.1 项目完成情况

本项目成功实现了一个**基于多智能体的智能旅行规划系统**，具备以下核心能力：

1. **多智能体协作**：9个专业Agent节点各司其职，通过Supervisor统一调度，支持评审循环优化
2. **RAG知识增强**：Qdrant向量数据库存储景点/行程知识，混合检索+CrossEncoder重排序提升检索质量
3. **地图服务集成**：高德地图API提供地址解析和路线规划，支持前端地图展示
4. **用户记忆系统**：Redis存储会话上下文，Mem0存储长期偏好，实现个性化服务
5. **完整API暴露**：FastAPI提供聊天、路线规划等接口，支持前端集成

### 7.2 存在问题

1. **并发安全问题**：同一用户多个Session同时更新Profile可能导致数据覆盖（已识别，待修复）
2. **本地LLM性能限制**：DeepSeek R1 1.5B模型在复杂推理时响应较慢
3. **知识库数据不足**：当前知识库数据量有限，影响RAG检索效果
4. **部分工具未完善**：航班、酒店查询功能为预留接口，实际数据依赖不足

### 7.3 项目收获

1. **大型语言模型应用**：深入实践了LLM的函数调用、结构化输出、多轮对话等能力
2. **多智能体系统设计**：掌握了多Agent协作、状态管理、条件路由、循环控制等核心概念
3. **RAG系统架构**：学习了向量数据库、混合检索、重排序等RAG关键技术
4. **系统设计能力**：完成了从需求分析、架构设计到编码实现的完整流程

### 7.4 未来改进方向

1. **并发安全修复**：实施Redis原子操作和分布式锁方案
2. **知识库扩充**：持续导入更多景点、行程数据，提升RAG效果
3. **模型升级**：考虑使用更大参数的LLM提升推理质量
4. **前端集成**：开发完整的前端界面，实现项目完整闭环
5. **功能扩展**：接入真实航班、酒店API，提供实际预订能力
