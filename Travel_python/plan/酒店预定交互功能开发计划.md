## 一、开发概述

### 1.1 功能范围

本次开发新增以下能力：

| 功能 | 说明 |
|------|------|
| 酒店意向选择 | researcher 查空房 → 用户选择意向酒店 |
| 酒店两阶段预定 | 意向选择 + confirm_and_book 正式预定 |
| 无房替代方案 | 原酒店被订走时提供替代酒店 |
| 无房闹钟提醒 | 用户选择设置闹钟，退房前提醒 |
| 多 flow 并行支持 | 同一会话可进行多个规划 |
| 流程状态恢复 | 中断后可从 Redis 恢复继续 |

### 1.2 不在本次范围内

- 闹钟提醒的定时任务执行机制（由 CronCreate 框架处理）
- 前端 UI 实现（由 Java/前端负责）
- Java 酒店接口的实现

## 三、阶段一：基础设施（P0）

> 目标：完成 Redis flow state + state.py 新字段，为后续开发铺底

### 3.1 redis_client.py 新增函数

新增 3 个函数：`save_flow_state`、`get_flow_state`、`clear_flow_state`

- key 格式：`agent:state:{session_id}:{flow_id}`
- TTL：3600 秒（1小时）
- 数据格式：JSON 序列化完整 state

**验证方式**：手动测试存取删流程

---

### 3.2 state.py 新增字段

在 `AgentState` TypedDict 中新增 4 个字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `flow_id` | `Optional[str]` | 当前 flow 唯一标识 |
| `interaction` | `Optional[dict]` | 交互状态（type/status/hotels/chosen/alternatives/alarm_set/message） |
| `needs_replan` | `Optional[bool]` | 是否需要重新规划 |
| `booking_status` | `Optional[str]` | 预定状态（confirmed/skipped/pending） |

---

### 3.3 web/api.py 接入 flow_id

修改点：

1. `ChatRequest` 模型新增 `flow_id` 字段
2. `ChatRequestFromJava` 模型新增 `flowId` 字段
3. `chat()` 函数入口：根据 `flow_id` 判断是否需要从 Redis 恢复 state

## 四、阶段二：核心流程改造（P1）

> 目标：完成 Intent_Recognition / Supervisor / task_analyzer / multi_agent_travel 的改造

### 4.1 Intent_Recognition.py 修改

修改内容：当 `interaction.status` 处于以下状态时，强制返回 `intent="plan"`，防止用户提问被识别为 QA

- `waiting_user_hotel`
- `waiting_user_decision`
- `waiting_user_alternatives`
- `waiting_user_alarm`

---

### 4.2 task_analyzer.py 修改

修改内容：

1. 生成 `flow_id`（8位 UUID）并存入 state，往后传递
2. 从用户消息中识别并提取 `start_date`（出发日期），结合 `days` 计算 `end_date`

---

### 4.3 supervisor.py 重写路由

完全重写 `supervisor_node` 函数，按以下顺序检查：

| 顺序 | 条件 | 路由目标 |
|------|------|---------|
| 1 | `final_plan` 已有 | `parse_plan` |
| 2 | `interaction.status` 以 `waiting_` 开头 | `user_interaction` |
| 3 | `needs_replan` 为 True | `task_analyzer`（并清空已有 state） |
| 4 | `task` 不存在 | `task_analyzer` |
| 5 | `research_results` 不存在 | `researcher` |
| 6 | hotel_select 类型但 `chosen` 为空 | `user_interaction` |
| 7 | `draft_plan` 不存在 | `planner` |
| 8 | 评分次数未达上限 | `critic` |
| 9 | 用户选了酒店且 `booking_status` 非 confirmed | `confirm_and_book` |
| 10 | 其他 | `final_optimizer` |

---

### 4.4 multi_agent_travel.py 注册新节点 + Redis 读写

修改点：

1. **注册新节点**：导入并注册 `user_interaction_node` 和 `confirm_and_book_node`
2. **入口逻辑**：根据 `flow_id` 从 Redis 恢复 state
3. **出口逻辑**：
   - `interaction.status` 以 `waiting_` 开头 → `save_flow_state`
   - 否则 → `clear_flow_state`
   - 若 `alarm_set=True` → 触发闹钟设置

## 五、阶段三：交互节点实现（P1-P2）

### 5.1 user_interaction_node.py 新增

**文件**：`app/agents/user_interaction_node.py`（新建）

统一交互入口，根据 `interaction.status` 调用对应 handler。

#### 4 个 handler：

| handler | 处理状态 | 场景说明 |
|---------|---------|---------|
| `handle_hotel_selection` | `waiting_user_hotel` | 等待用户从列表中选择酒店 |
| `handle_no_hotel_decision` | `waiting_user_decision` | researcher 发现全部没房 |
| `handle_hotel_alternatives` | `waiting_user_alternatives` | confirm 时原酒店没房，有替代 |
| `handle_hotel_alarm_decision` | `waiting_user_alarm` | confirm 时原酒店没房，无替代，问是否设闹钟 |

#### 工具函数：

- `parse_hotel_choice`：解析用户输入（序号/名称/模糊匹配）返回酒店对象
- `build_hotel_selection_prompt`：构建酒店选择提示
- `build_no_hotel_prompt`：构建无房时提示
- `build_alternatives_prompt`：构建替代酒店选择提示
- `build_alarm_prompt`：构建闹钟设置提示

#### 实现顺序：
1. `parse_hotel_choice`（核心解析逻辑）
2. `handle_hotel_selection`
3. `handle_no_hotel_decision`
4. `handle_hotel_alternatives`
5. `handle_hotel_alarm_decision`
6. 各种 `build_*_prompt` 工具函数

---

### 5.2 confirm_and_book_node.py 新增

**文件**：`app/agents/confirm_and_book_node.py`（新建）

确认并预定酒店节点，实现两阶段预定中的第二次确认。

#### 逻辑流程：

```
进入节点
    │
    ├── chosen 为空 → 直接跳过（用户不要酒店）
    │
    ▼
调用 Java 接口查询房间是否还有
    │
    ├── 有空房 → 调用 Java 接口正式预定
    │                │
    │                ├── 成功 → booking_status="confirmed"
    │                └── 失败 → 进入无替代流程
    │
    └── 没空房
            │
            ├── 有替代酒店 → interaction.status="waiting_user_alternatives"
            │                  返回替代列表
            │
            └── 无替代酒店 → interaction.status="waiting_user_alarm"
                             返回闹钟询问
```

## 七、接口对接说明

### 7.1 需要 Java 提供或实现的接口

| 接口 | 路径 | 方法 | 参数 | 返回 |
|------|------|------|------|------|
| 查询空房 | `/api/hotel/query` | POST | `hotel_id`, `checkin`, `checkout` | `{has_rooms, similar_hotels[]}` |
| 正式预定 | `/api/hotel/book` | POST | `hotel_id`, `user_id`, `checkin`, `checkout` | `{success, booking_id, error}` |

### 7.2 Python 调用 Java 接口格式

**查询空房**：
```json
POST /api/hotel/query
{"hotel_id": "hotel_123", "checkin": "2026-08-01", "checkout": "2026-08-06"}

返回:
{"has_rooms": true, "similar_hotels": [...]}
```

**正式预定**：
```json
POST /api/hotel/book
{"hotel_id": "hotel_123", "user_id": 1, "checkin": "2026-08-01", "checkout": "2026-08-06"}

返回：
{"success": true, "booking_id": "booking_789", "error": null}
```

### 7.3 闹钟回调

说明：闹钟触发时由 Java 自行处理或通过消息队列通知 Python，**本项目暂不实现此接口**，由 Python CronCreate 框架处理。

## 九、联调说明

### 9.1 与 Java 前端联调

| 阶段 | 前端动作 | Python 返回内容 |
|------|---------|----------------|
| 发起规划 | 调用 `/api/chat`，不传 `flow_id` | 返回 `flow_id` |
| 选酒店 | 传 `flow_id` + 用户选择 | `interaction.status="waiting_user_hotel"` 时返回酒店列表 |
| 无房-选替代 | 同上 | `status="waiting_user_alternatives"` 时返回替代列表 |
| 无房-设闹钟 | 同上 | `status="waiting_user_alarm"` 时询问是否设闹钟 |
| 流程结束 | 显示规划结果 | `final_plan` / `parsed_plan` |

**前端判断是否继续等待用户**：检查 `result.interaction.status` 是否以 `waiting_` 开头

### 9.2 与 Java 酒店接口联调

1. 本地测试：使用 Mock 数据模拟 Java 接口响应
2. 联调测试：启动 Java 服务，验证 Python 调用 Java 接口
3. 超时处理：确保 timeout=10 生效
